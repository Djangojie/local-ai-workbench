# 本机多模型工作台

本 Skill 操作用户克隆的本机工作台。先定位当前工作台目录并读取其中的 `README.md`；不要假定不同机器的路径、凭证或工具状态相同。

## 选择入口

- 查看状态、运行已保存流程、恢复人工交接、运行普通对比：优先使用已连接的 `local_ai_workbench` MCP 工具。若不可用，可调用本机 `http://127.0.0.1:8765/api/`，或在页面操作。
- 运行内置编程排错题：点击页面“运行编程实测”，或执行本 Skill 的 `scripts/workbench_probe.py coding-benchmark`。它会触发真实模型调用。
- 用户希望“看群聊”：打开本机页面。群聊按协作阶段展示完成后的结果；并行候选不是实时逐条互相发言。
- 修改节点、模型参数或密钥：使用页面“流程画布”和“服务商与密钥”。页面只显示密钥状态。不要在聊天、日志、Skill 或配置示例中输出密钥。

## 运行前检查

1. 用 `scripts/workbench_probe.py status` 只读检查服务和各工具状态。若服务未启动，核对 8765 端口占用进程；只在确认是旧版工作台进程后停止它，再从工作台目录运行 `python server.py`。服务仅监听 `127.0.0.1`。
2. 需要真实调用时，确认相应服务商密钥状态和本机工具就绪；不要把“已配置”“本机安装”写成“真实请求成功”。Kimi 桌面版和豆包工作版是人工交接，不是自动 API 节点。
3. 任务应写明输入、预期输出和可核验的验收条件。编程排错优先使用实际测试、复现命令、失败用例和修复证据；把模型盲审评分标成估计。

## 判断结果

- 先看每个候选的状态、错误和测试证据，再看选择理由。Hermes 或其他工具失败时如实报告，不能算作已参与成功协作。
- 内置 `first_pair` 编程题有 11 个公开用例，只能证明这道题当次表现。若单模型代码超出受限执行器允许的语法，应报告“未评分/无法公平判优”，不能把它计作 0 分并宣称集群胜出。
- 只有**同一任务、同一可执行测试**下，多模型候选得分严格高于单模型基线，才能报告该任务集群胜出；持平时报告持平。若最佳结果来自单个 Pi/Harness 候选，应称“多候选择优”，不要称为合成推理带来的提升。
- 用户要求整体优于单个 AI 时，建立覆盖其真实编程与排错场景的固定题集，记录成功率、耗时和可见 API 用量；单题胜负或模型自评不足以证明总体优势。CLI 用量不可见时不要推算总成本。

## 操作边界

工作台的 Pi 节点是受限文本模式；Harness 可能仍调用自身工具，不能视为操作系统沙箱。内置代码执行器只适合短函数题，不要把任意仓库生成代码交给它直接运行。修改真实项目时仍需在该项目中检查差异并运行对应测试。

工作台本体说明见仓库根目录的 `README.md`。
